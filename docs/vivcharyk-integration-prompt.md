# Промпт для проєкту сайту «Вівчарик»: підготовка до підключення ONEKNIGHT

> Вставте текст нижче (від «Контекст») на початку роботи над кодом сайту або додайте його в `CLAUDE.md` проєкту
> розділом «Інтеграція з ONEKNIGHT». Він не змінює архітектуру з `docs/`: сайт будується за блупринтом, зі своїм
> бекендом. Він лише закладає місце, куди потім без переписування «вкрутиться» панель ONEKNIGHT.

## Контекст

Сайт «Вівчарик» будується за блупринтом у `docs/` (порядок авторитету — у `CLAUDE.md`) зі своїм бекендом і своєю
адмінкою. Пізніше до нього підключиться **ONEKNIGHT** — зовнішня панель керування бізнесом (замовлення, клієнти,
доставка, товари, відгуки, аналітика). Після підключення частина даних житиме в ONEKNIGHT, а сайт отримуватиме їх
через API й вебхуки.

Завдання зараз: **будувати сайт так, щоб це підключення було заміною однієї реалізації на іншу, а не переписуванням.**
Нічого не інтегруй з ONEKNIGHT зараз і не змінюй блупринт. Закладай лише межі, контракти й місця підключення,
описані нижче.

## Що вже вміє ONEKNIGHT (станом на 30.09.2026)

Орієнтуйся лише на це. Не вигадуй інших ендпойнтів: чого немає — того немає. Актуальна документація —
`https://oneknight.pro/docs/api` (локально `http://localhost:8080/docs/api/`).

**Два входи API**
- `/api/public/*` — для браузера. Публічний ключ сайту `sk_` + 32 hex, заголовок `x-site-key`. Працює лише
  з домену сайту (перевірка Origin).
- `/api/v1/*` — для **сервера сайту**. Секретний ключ `ok_sec_…` у заголовку `Authorization: Bearer …`.
  - Запит із браузера відхиляється з `403 secret_key_in_browser`.
  - Ліміти рахуються на сайт, а не на IP: 600 читань за хвилину, 300 замовлень за 10 хвилин.
  - Несумісні зміни підуть у `/v2`; `/v1` працюватиме ще щонайменше 6 місяців.

**Ендпойнти `/api/v1`**
- `GET /site` — `{ id, domain, name, business, verified, publicKey }`.
- `GET /products`, `GET /products/{id}` — товари сайту.
  - Поля: `id, sku, name, description, categoryId, price, oldPrice, discountPercent, availability, orderDays,
    inStock, stock, fewLeft, photo, photos[], attributes[{name,value}], warrantyMonths, weightG`.
  - `availability`: `in_stock | to_order | expected | out`.
  - Ціни — у гривнях числом.
  - **Варіантів (розмір × колір), одиниць «кг / моток / метр» і перекладів поки немає.** Це заплановано й буде
    доведено під «Вівчарик» перед підключенням.
- `GET /categories` — `[{ id, name, parentId }]`, дерево.
- `POST /orders` — замовлення. Відповідь `201 { number, total, status }`, або `409` (`out_of_stock`,
  `unavailable`, `unknown_product`).
  - Тіло: `{ customer: { name, phone, email? }, items: [{ productId, qty 1..99 }], delivery: { method:
    novaposhta|ukrposhta|pickup|courier, city?, branch?, address? }, payment: cod|iban|card, comment?, analytics?,
    customerIp? }`.
  - Ціни й назви ONEKNIGHT бере зі свого каталогу, а не із запиту. Залишок резервується атомарно.
- `GET /orders/{number}` — статус для сторінки замовлення: `status, statusName, paymentStatus, prepaid, total,
  items, delivery, payment, waybill, createdAt, history[]`.

**Статуси ONEKNIGHT**
- Замовлення: `new, confirmed, shipped, done, cancelled, returned`. У бізнесу можуть бути свої підстатуси —
  приходять у `statusName`.
- Оплата: `unpaid, prepaid, paid, refunded`.

**Вебхуки**
- До 3 адрес на сайт, кожна зі своїм набором подій.
- Події:
  - `order.created`, `order.status_changed`, `order.payment_changed`;
  - `product.changed` (`action: created|updated|deleted`), `stock.changed`, `category.changed`.
- Тіло: `{ id, type, createdAt, siteId, data }`. Дані короткі (ідентифікатори й новий стан) — актуальне бери з API.
- Заголовки: `x-oneknight-event`, `x-oneknight-delivery`,
  `x-oneknight-signature: t=<unix>,v1=<hex HMAC-SHA256(secret, t + "." + raw body)>`.
- Відповідь 2xx означає «доставлено». Інакше повтори через 1, 5, 30 хв, 2 і 12 год. Та сама подія може прийти двічі.

**ok.js** (аналітика й віджети в браузері): `<script src="https://oneknight.pro/ok.js" data-key="sk_…" defer>`.
- Атрибути:
  - `data-ok-product="<id>"` — сторінка товару;
  - `data-ok-cart` — кошик;
  - `data-ok-phone`, `data-ok-name` — поля, з яких ONEKNIGHT збирає незавершені кошики;
  - `data-ok-reviews`, `data-ok-stars` — віджети відгуків.
- Функції: `oneknight.track()`, `oneknight.context()` (передається в `analytics` замовлення), `oneknight.cart([...])`,
  `oneknight.product(id)`.
- Кліки на `tel:`, `viber:`, `t.me` рахуються самі.

## Як будувати сайт, щоб потім підключити ONEKNIGHT

### 1. Межі даних через інтерфейси (порти)
- Уся бізнес-логіка звертається до даних лише через інтерфейси доменних сервісів, а не напряму до БД. Мінімальний
  набір:
  - `CatalogSource` — товари, варіанти, категорії, залишок, наявність;
  - `OrderSink` — створення замовлення, його статус;
  - `ReviewSource` — відгуки, створення відгуку;
  - `CustomerDirectory`;
  - `AnalyticsSink`.
- Зараз кожен інтерфейс реалізує `Local*` (власна БД за блупринтом). Потім з'явиться `OneKnight*`: HTTP-клієнт до
  `/api/v1`.
- Перемикання — через конфіг (`DATA_BACKEND=local|oneknight`, окремо для кожного порту), а не правками по коду.
- UI, SSR і API сайту не повинні знати, звідки дані.

### 2. Зовнішні ідентифікатори
- У таблицях товару, варіанта, категорії, замовлення, клієнта й відгуку додай nullable-поле `externalRef`
  (формат `oneknight:<id>`) з унікальним індексом.
- Власні `id` сайту не змінюються. Зв'язок із ONEKNIGHT іде лише через `externalRef`.
- Номер замовлення сайту (`VCH-YY-NNNN`) і номер ONEKNIGHT (число) — різні сутності. Зберігай обидва, коли з'явиться
  другий.

### 3. Однакові формати на межі
- Гроші всередині — ціле в копійках (як у блупринті). На межі з ONEKNIGHT `/v1` — гривні числом. Конвертація лише
  в адаптері.
- Телефон — E.164 (`+380…`). Дати — ISO 8601 UTC.
- Статуси: заведи одну таблицю відповідності статусів сайту ↔ ONEKNIGHT (замовлення й оплата) в адаптері, а не
  розкидані `if`.
  - У блупринті статусів більше (`IN_PRODUCTION`, `PACKING` тощо). Мапуй їх на групи ONEKNIGHT і тримай оригінал
    у `statusName`.

### 4. Вихідні події сайту (outbox)
- Кожна важлива зміна (нове замовлення, скасування, відгук) пишеться в таблицю `outbox` у тій самій транзакції.
- Окремий воркер відправляє записи з `outbox`. Зараз — у власні сповіщення, потім — ще й у ONEKNIGHT.
- Ідемпотентність: у кожного запису свій ключ, повтор не дублює замовлення.

### 5. Приймач вебхуків (заготовка)
- Маршрут `POST /api/integrations/oneknight/webhook`:
  - сире тіло;
  - перевірка підпису HMAC-SHA256 за сталий час;
  - відхиляти `t`, старший за 5 хвилин;
  - ідемпотентність за `id` (таблиця оброблених подій);
  - відповідь 204 одразу, а обробка — у фоні.
- Обробник подій порожній, поки `DATA_BACKEND` не `oneknight`. Потім він скидає кеш і перегенеровує сторінки:
  `product.changed` і `stock.changed` → сторінки товару й списки; `category.changed` → меню.
  Так само, як блупринт робить purge після змін в адмінці.

### 6. Кеш і перегенерація в одному місці
- Одна функція `revalidate(entity, id)`. Її викликає і власна адмінка, і приймач вебхуків.
- Жодних ручних purge по коду.

### 7. Секрети й конфіг (лише на сервері)
- Змінні `ONEKNIGHT_API_URL`, `ONEKNIGHT_SECRET_KEY`, `ONEKNIGHT_WEBHOOK_SECRET` зберігай у змінних середовища
  сервера. У клієнтський бандл вони не потрапляють ніколи.
- Змінна `ONEKNIGHT_PUBLIC_KEY` — для ok.js, її можна показувати в браузері.
- Порожні значення = інтеграція вимкнена, сайт працює сам.

### 8. ok.js — одразу розміти сторінки
- Навіть поки ONEKNIGHT вимкнено, розмічай сторінки атрибутами з розділу «ok.js» вище: товар, кошик, поля телефону
  й імені в оформленні. Тоді після ввімкнення аналітика, незавершені кошики й віджети запрацюють без правок шаблонів.
- Сам скрипт підключай лише коли є `ONEKNIGHT_PUBLIC_KEY`, і після згоди на cookies, якщо так вимагає блупринт.
- Під час оформлення бери `oneknight.context()` (якщо скрипт є) і зберігай у замовленні: потім воно піде
  в `analytics`.

### 9. Контрактні тести
- Для адаптера `OneKnight*` пиши тести на записаних відповідях (fixtures) з прикладів вище, без мережі.
- Контракт — лише поля, перелічені в цьому документі.

### 10. Журнал розбіжностей
- Веди файл `docs/oneknight-integration.md`: кожна потреба сайту, якої немає в API ONEKNIGHT (варіанти, одиниці
  кг / моток / метр, переклади, свій розмір, депозит за доставку, передоплата, фіскальні чеки, промокоди покупців,
  контент і т. д.).
- Для кожного пункту: що потрібно, поля, звідки в блупринті.
- За цим списком ONEKNIGHT доробить API перед підключенням.

## Чого не робити
- Не викликати ONEKNIGHT з браузера із секретним ключем. Секретний ключ живе лише на сервері.
- Не дублювати логіку ONEKNIGHT (ціни, резерв залишку) на боці сайту для випадку «oneknight». Там сайт лише
  передає запит і показує відповідь.
- Не вигадувати ендпойнти, поля чи події, яких немає в цьому документі чи на `/docs/api`. Якщо чогось бракує —
  запиши в `docs/oneknight-integration.md`.
- Не змінювати блупринт і рішення клієнта заради інтеграції.
